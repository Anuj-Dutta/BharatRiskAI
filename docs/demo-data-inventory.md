# Demo, Mock, Hardcoded, and Production-Path Inventory

**Scope:** P1-02 audit of first-party source, documentation, and tests as found on 2026-11-05. This is an inventory and remediation plan; no demo data, fixtures, fallbacks, or production code were deleted or changed.

## Classification

- **Test fixture:** data intentionally owned by a test and isolated from runtime paths.
- **Intentional fallback:** an explicitly selected demo/offline path that keeps local development or degraded operation usable. It must remain visibly labeled and must not be reported as live/official data.
- **Production-path defect:** a synthetic, defaulted, or hardcoded value can be used by a live path or presented with a live/ready/online status.

## Duplicate sources of demo truth

The same five/eight Kolkata zones are represented in multiple places:

- [`database/seed.py`](../database/seed.py#L12-L17)
- [`backend/database/local_db.py`](../backend/database/local_db.py#L24-L161)
- [`frontend/src/services/demoData.js`](../frontend/src/services/demoData.js#L3-L13)
- [`ml/training/train.py`](../ml/training/train.py#L20-L35) uses synthetic distributions rather than these rows

This duplication is a maintenance risk: values, risk scores, report counts, and zone counts can diverge. The replacement is one versioned demo fixture/schema consumed by local DB seeding and the frontend demo provider, with an explicit provenance field. It must remain separate from any approved production/authoritative dataset.

## Priority remediation order

1. **Block synthetic production responses:** remove runtime auto-training and silent model/ingestion fallbacks from live mode; expose `BLOCKED`/degraded status.
2. **Correct operational status:** replace static `ONLINE`, `mesh_connected`, and synthetic risk trends with measured state and persisted observations.
3. **Separate demo mode:** require an explicit environment/provider flag and propagate `source=demo`/`is_synthetic`.
4. **Consolidate demo fixtures:** create one versioned local fixture consumed by the backend seed/local DB and frontend demo provider.
5. **Replace confidence values:** add a model calibration contract or return unavailable confidence.
6. **Preserve and strengthen tests:** add contract tests for provenance, blocked live mode, and offline queue replay before implementing the changes above.

## Human approvals and data required

- Approval of the authoritative zone boundary/population/elevation/drainage/flood-history sources.
- A decision on whether production should fail closed or permit a clearly labeled degraded heuristic mode.
- A calibrated model artifact and calibration metadata for any confidence field.
- Provider credentials/endpoints and freshness/quality contracts for live weather, satellite, population, terrain, and alert integrations.
- Approval of Supabase/local fallback policy and production RLS policy.
